# Мост РФ → Европа для Remnawave

Два скрипта, которые превращают пару нод Remnawave в мост:

```
телефон клиента ──► RU-сервер (вход) ──► EU-сервер (выход) ──► интернет
                     │
                     └── российские сайты выходят сразу отсюда
```

Зачем это нужно: из России часто не достучаться напрямую до европейского сервера.
Провайдер режет или замедляет такие соединения. До российского сервера клиент
достучится всегда, а дальше трафик идёт уже между двумя серверами в дата-центрах,
и этот канал работает стабильнее.

Всё, что «за кадром», скрипты делают сами:

| | что ставится на сервер |
|---|---|
| **Заглушка (selfsteal)** | маленький веб-сервер Caddy на `127.0.0.1:9443`. Без него REALITY не работает, подробнее в разделе [Вопросы](#вопросы) |
| **Фаервол** | закрывает всё лишнее. На EU-сервере порт моста открыт **только** для RU-сервера |
| **Ключи REALITY** | генерируются сами и хранятся на сервере |
| **Готовый конфиг для панели** | скрипт печатает JSON, его нужно просто вставить |

Панель Remnawave скрипты **не трогают**. Всё, что делается в панели, делаете вы руками по этой инструкции.

## 1. Что нужно заранее

- **Панель Remnawave** и её **IP-адрес**. Он понадобится для фаервола, потому что к нодам должна подключаться только панель.
- **Два сервера** на Ubuntu 22.04/24.04 или Debian 12 с доступом `root` по SSH:
  - **RU**: российский, сюда подключаются клиенты;
  - **EU**: европейский, через него трафик выходит в интернет.
- На **обоих** серверах уже стоит **нода Remnawave** (добавлена в панели: *Nodes → Create*, установлена командой, которую выдаёт панель), и в панели нода зелёная.
- **Домен** для каждого сервера, например `ru.example.com` и `de.example.com`.
  Хорошо, если A-запись указывает на сервер, но для работы моста это **не обязательно**: имя используется только как «вывеска» (SNI).

> ⚠ Если на серверах уже настроено что-то другое (другие инбаунды, сайты на 443 порту), мост это **заменит**. Ставьте на чистые ноды или на те, которые не жалко.

## 2. Как подключиться к серверу

С компьютера (Windows: «Терминал» или PowerShell; macOS/Linux: «Терминал»):

```bash
ssh root@IP_СЕРВЕРА
```

Введите пароль от сервера. Символы при вводе не отображаются, так и должно быть.
Дальше все команды выполняются в этом окне.

Скачать скрипты на сервер:

```bash
apt-get update && apt-get install -y git
git clone https://github.com/R17vera/remnawave-ru-bridge.git
cd remnawave-ru-bridge/scripts
```

> Без git можно скачать два файла напрямую:
> ```bash
> curl -fsSLO https://raw.githubusercontent.com/R17vera/remnawave-ru-bridge/main/scripts/eu-exit-setup.sh
> curl -fsSLO https://raw.githubusercontent.com/R17vera/remnawave-ru-bridge/main/scripts/ru-entry-setup.sh
> ```

## 3. Служебный пользователь

Это обычный пользователь в панели, но не для людей: под ним **RU-сервер подключается к EU-серверу**.

1. В панели: *Users → Create*. Имя, например, `bridge-service`.
2. **Без лимита трафика, без срока окончания.** Через него пойдёт трафик **всех** клиентов моста.
3. Откройте пользователя и скопируйте его **VLESS UUID**, он выглядит так: `3b1f6c2e-8d4a-4f7b-9e21-5a6c0d9b7e44`.

> ⚠ Никогда не делайте этому пользователю **Revoke** и не отключайте его: UUID сменится, и мост ляжет целиком.

## 4. EU-сервер (выход)

Подключитесь к **EU**-серверу (раздел 2) и запустите:

```bash
bash eu-exit-setup.sh \
  --tag DE \
  --domain de.example.com \
  --ru-ip IP_RU_СЕРВЕРА \
  --panel-ip IP_ПАНЕЛИ \
  --uuid UUID_СЛУЖЕБНОГО_ПОЛЬЗОВАТЕЛЯ
```

| параметр | что писать |
|---|---|
| `--tag` | короткое имя страны латиницей: `DE`, `NL`, `EST`… Из него складываются имена в конфигах |
| `--domain` | домен EU-сервера |
| `--ru-ip` | IP RU-сервера. Только ему будет открыт вход в мост. Несколько IP — через запятую |
| `--panel-ip` | IP панели |
| `--uuid` | UUID служебного пользователя из раздела 3 |

Скрипт работает около минуты и в конце выводит две вещи:

1. **EU config profile**: большой блок JSON для панели;
2. **Exit token**: одна длинная строка, начинается с `bridge1:`. Она понадобится для RU-сервера.

Обе вещи также сохраняются на сервере. Показать их ещё раз: `bash eu-exit-setup.sh --print`.

### ⚠ Обязательно: подтвердить фаервол

Сразу после скрипта, **не закрывая текущее окно**, откройте **второе** окно терминала и
подключитесь к этому же серверу ещё раз (`ssh root@...`).

- **Получилось** — вернитесь в первое окно и выполните:
  ```bash
  bash eu-exit-setup.sh --confirm
  ```
- **Не получилось** — ничего не делайте. Через **5 минут** фаервол сам снимется, и доступ вернётся.

Это защита от того, чтобы случайно закрыть себе доступ к серверу.

## 5. Панель: профиль EU

1. *Config Profiles → Create*. Имя латиницей, например `DE Exit Bridge`.
2. Удалите всё, что панель подставила по умолчанию, и вставьте **EU config profile** целиком. Сохраните.
3. *Nodes →* ваша EU-нода → выберите профиль `DE Exit Bridge` и включите инбаунд `DE_BRIDGE_IN_FROM_RU`.
4. *Internal Squads*: создайте сквад, например `bridge-DE`, отметьте в нём **только** инбаунд `DE_BRIDGE_IN_FROM_RU`.
5. Добавьте в этот сквад **служебного пользователя**. Клиентов туда **не** добавляйте.

## 6. RU-сервер (вход)

Подключитесь к **RU**-серверу и запустите (exit token — та длинная строка из раздела 4, **в кавычках**):

```bash
bash ru-entry-setup.sh \
  --domain ru.example.com \
  --panel-ip IP_ПАНЕЛИ \
  --exit 'bridge1:....длинная строка....'
```

| параметр | что писать |
|---|---|
| `--domain` | домен RU-сервера |
| `--panel-ip` | IP панели |
| `--exit` | токен EU-сервера. Несколько стран — несколько `--exit` подряд (см. раздел 9) |
| `--allow IP:ПОРТ` | *(необязательно)* открыть ещё порт для конкретного IP. Например, мониторинг хостера: `--allow 92.53.116.12,92.53.116.111:10050` |
| `--no-ru-direct` | *(необязательно)* пускать в Европу **всё**, включая российские сайты |

Порт для клиентов первой страны — **443**, второй — 8443, дальше 2053, 2083, 2087, 2096.
Свой порт можно задать так: `--exit 'bridge1:...@8443'`.

В конце скрипт выводит:
1. **RU config profile**: JSON для панели;
2. **Hosts for clients**: готовые настройки хостов;
3. **Squads**: кого в какой сквад.

И снова **подтвердите фаервол**, как в разделе 4: второе окно, вход, затем `bash ru-entry-setup.sh --confirm`.

---

## 7. Панель: профиль RU, сквады, хосты

1. *Config Profiles → Create* → `RU Bridge` → вставьте **RU config profile** целиком.
2. *Nodes →* RU-нода → профиль `RU Bridge`, включите инбаунд `ENTRY_DE_IN`.
3. *Internal Squads*: в сквад **клиентов** добавьте инбаунд `ENTRY_DE_IN`.
4. *Hosts → Create*:

| поле | значение |
|---|---|
| Remark | как клиенты увидят сервер в приложении, например `🇩🇪 Германия` |
| Inbound | `RU Bridge` → `ENTRY_DE_IN` |
| Address | домен RU-сервера (или его IP) |
| Port | `443` (или тот, что выдал скрипт) |
| SNI | домен RU-сервера |
| Fingerprint | `firefox` |
| остальное | пусто / по умолчанию |

Публичный ключ и shortId панель подставит сама.

> ⚠ В хосте всегда указывается **RU-сервер**. Если указать EU-сервер, клиент не подключится: EU открыт только для RU.

## 8. Проверка

**Плечо RU → EU** проверяется прямо с RU-сервера:

```bash
bash ru-entry-setup.sh --check
```

```
RU -> EU legs (service user, from this box):
  OK    DE: exit IP 203.0.113.20, 1 MB in 0.41s
```

`OK` — мост между серверами работает. `FAIL` — смотрите раздел 10.

**Целиком**: обновите подписку в приложении (Happ, v2rayTun, Hiddify…), подключитесь к новому серверу и откройте 2ip.ru.
Должен показаться **IP EU-сервера**. Российские сайты при этом откроются напрямую с RU-сервера, это нормально.

## 9. Добавить ещё страну

1. Новый EU-сервер: раздел 4 с другим `--tag` (например `NL`), затем раздел 5.
2. На RU-сервере запустите `ru-entry-setup.sh` **со всеми** токенами сразу, старыми и новым:
   ```bash
   bash ru-entry-setup.sh --domain ru.example.com --panel-ip IP_ПАНЕЛИ \
     --exit 'bridge1:...токен DE...' \
     --exit 'bridge1:...токен NL...'
   ```
   Ключи для уже существующих стран не меняются, поэтому старые хосты продолжат работать.
   Токены старых стран можно взять на их EU-серверах: `bash eu-exit-setup.sh --print`.
3. В панели замените RU-профиль новым, включите на RU-ноде новый инбаунд `ENTRY_NL_IN`, добавьте его в сквад клиентов и создайте хост на новом порту (раздел 7).
4. `bash ru-entry-setup.sh --check`: должно быть `OK` по каждой стране.

## 10. Если что-то не работает

| что видно | в чём дело | что делать |
|---|---|---|
| `--check`: **FAIL** | служебного пользователя нет на EU-инбаунде | раздел 5, п. 4–5. Проверить, что пользователь активен и не истёк |
| `--check`: **FAIL** | на EU-ноде не включён инбаунд или не тот профиль | *Nodes →* EU-нода → профиль и галочка инбаунда |
| `--check`: **FAIL** после пересоздания EU | на EU сгенерировались новые ключи, а в RU-профиле старые | взять новый токен (`--print` на EU), перезапустить RU-скрипт, обновить RU-профиль в панели |
| `--check` **OK**, а в приложении не пингуется | хост смотрит не туда | в хосте адрес **RU**-сервера, порт и инбаунд `ENTRY_..._IN` из вывода скрипта |
| подключается, но интернета нет | клиентов нет в скваде с `ENTRY_..._IN` | раздел 7, п. 3 |
| нода в панели стала красной | панель сменила IP | перезапустить оба скрипта с новым `--panel-ip` |
| после перезагрузки сервера всё сломалось | включён `nftables.service`: он стирает правила docker и ноды | `systemctl disable --now nftables` и перезагрузить |
| старые клиенты не подключаются | у них старый ключ или старый хост | обновить подписку в приложении |

Полезные команды на сервере:

```bash
systemctl status caddy                    # заглушка работает?
systemctl status bridge-firewall          # фаервол включён?
nft list table inet bridge_fw             # какие порты открыты
docker logs --tail 50 remnanode           # логи ноды
```

---

## 11. Откат

Снять фаервол:
```bash
bash eu-exit-setup.sh --rollback     # на EU
bash ru-entry-setup.sh --rollback    # на RU
```

Остановить заглушку: `systemctl disable --now caddy`.
Ключи и прошлые настройки лежат в `/root/eu-bridge` и `/root/ru-bridge`, удалите их, если они больше не нужны.
Профили в панели верните на прежние вручную.

## Вопросы

**Зачем заглушка, если клиенты ходят на RU, а EU вообще закрыт?**
REALITY устроен так, что на **каждое** подключение xray обращается к «настоящему» сайту (`target`)
и маскирует своё соединение под его TLS-ответ. Без живого TLS-сайта в `target` REALITY отбивает
всех, и своих тоже. Внешний сайт (google, microsoft…) на xray 26.x в этой роли работает плохо,
поэтому ставится свой Caddy на `127.0.0.1`. Наружу он не виден и занимает ~20 МБ памяти.

**Почему между серверами REALITY, а не «голый» VLESS?**
Трафик из РФ за границу проходит через ТСПУ. Голый VLESS виден по сигнатуре и легко режется,
а REALITY выглядит как обычный HTTPS.

**Что значат `dns` и `UseIPv4` в профилях?**
Сервер узнаёт адреса сайтов через зашифрованный DNS (Cloudflare и Google) и только по IPv4.
Это защищает от подмены ответов DNS хостером и от кривого IPv6 у хостера.

**Зачем `minClientVer: "0.0.0"`?**
Новые xray по умолчанию молча не пускают клиентов со старым ядром, а также mihomo/sing-box:
они просто попадают на заглушку. `0.0.0` отключает эту проверку.

**Можно ли запускать скрипты повторно?**
Да. Ключи сохраняются, конфиги пересобираются, фаервол перезаписывается.
Перед каждой правкой скрипт кладёт копию старого рядом с ключами.

**Посмотреть результат, ничего не меняя на сервере?**
Добавьте `--dry-run`: скрипт только сгенерирует ключи и напечатает конфиги.
